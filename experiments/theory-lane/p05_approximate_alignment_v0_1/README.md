# Approximate sign repair assay

This development experiment compares a fixed approximate donor alignment with
unaligned donors, own backup signs and a recipient-only sign completion solver.
All 64 exposed cases and both fixed donors are retained. The native assessment has
nine records and 16 fresh paired injury/noise draws, plus original-injury controls.

The exact-alignment failure remains in the preceding audit. The new method permits
weighted sign disagreements, with 16 starts and at most 64 sweeps. It receives
surviving records and fixed port locations, without missing own signs, writer
provenance or future outcomes. Completion receives the recipient record alone to
infer signs; every hybrid still receives the same protected incoming magnitudes
and common support.

[PROTOCOL.md](PROTOCOL.md) defines the objective, inference and stopping rules.
[PREDICTION.json](PREDICTION.json) specifies the directional development forecast.
[prepared/FEASIBILITY.json](prepared/FEASIBILITY.json) records 192 independently
checked optimization problems. Every donor graft changes and is inequivalent to
the corresponding unaligned graft under port-preserving whole-network switching.
Those structural checks do not establish a performance benefit.

`benchmark/COMPLETE.json` records timing on duplicated known native reads. The
scientific run executes only a frozen copy under `runs/pilot_v1/inputs`. Its PID,
log, durable status and eventual report are in `runs/pilot_v1`. Read completion or
failure when requested; do not automatically poll or launch a successor.

All numerical libraries use one thread. The completed run checks known original
replays, exact masked-backup controls, dual-task erasure controls, independent
native dynamics, scores and block summaries. Hashes establish provenance rather
than preregistration. The eight blocks and selected failures are already exposed.

Preparation and runner scripts refuse to overwrite outputs. Reproduction should
use a new versioned sibling directory containing source files but no prepared,
benchmark or run outputs. Run preparation, tests, benchmark and freeze in order
with the project Python environment. Long jobs require the persistent host launch
and the shared CPU-budget check described in the lane run policy.
