# TT022 first rewrite: a strong lead in the replacement-fill pattern

The saved-data diagnostic localizes a large informative-record loss to the
first repair episode and finds a pronounced dependence on which half of the
target survives. The native replacement fill is −1. Capture copies that fill
into memory along with the surviving body. Its spatial pattern can support,
oppose or compete with the intended task pattern. The outgoing record changes
in the corresponding directions. This is a mechanistic lead, not a completed
causal test of the fill hypothesis.

All four exposed TT022 blocks, four futures, sixteen positions, both families
and seven policies are retained. The analysis was designed after the aggregate
serial outcomes were inspected. It uses no new dynamics or receiving assays.
The injury strata were chosen post hoc, then defined from task and mask without
selecting on outcome. There is no significance verdict or fresh confirmation.

Repeated and one-time capture begin with byte-identical records, developed
bodies and injuries in all 512 paired future-record cases across both families.
Their next receiving environments also match. Only their outgoing packet
crosses into that next body. The first repair episode changes both captured
memory feedback and writing; their individual contributions are not isolated.

| Family | Identical first developed body | Next body after capture/write | Next body with initial packet preserved | Paired difference |
| --- | ---: | ---: | ---: | ---: |
| Common | 69.922% | 64.844% | 69.141% | −4.297 pp |
| Informative | 90.234% | 61.328% | 89.844% | −28.516 pp |

These next-body comparisons use the same receiving environment across policies;
the first and second bodies use different environments. For common records,
capture improves 20, worsens 31 and ties 205 paired draws. For informative
records it improves 14, worsens 87 and ties 155. The four informative block
differences are −14.062, −39.062, −26.562 and −34.375 percentage points. Each
family contains 256 future draws nested in four population blocks, not 256
independent population replicates.

The targets are four signed horizontal/vertical half-plane patterns. When an
injury aligns with the target boundary, the retained half contains either its
positive or its negative target cells. An injury across that boundary retains
both polarities. All three groups are shown below.

The fill is not a neutral missing value. It is the actual negative resting
state supplied by this simulator, with copy jitter of 0.05. Before jitter,
the replacement fill contributes +0.5 to the intended code projection when
the positive half survives, −0.5 when the negative half survives, and zero
when both target polarities survive. In the last case it instead supplies
a competing spatial half-plane pattern. For every injury, its projection
onto the signed retained-versus-replaced mask is +0.5. Mean-centering removes
a constant offset but retains this spatial component.

The independent scalar decomposition confirms this in the actual saved
captures. For informative records with the negative half retained, the surviving
body contributes +0.294331 to the intended projection, the replacement fill
contributes −0.500000, and original jitter contributes +0.000188. Their sum is
−0.205481. The bounded writer target, tanh(R), likewise points against the
intended code on average: −0.157046. Thus a body that developed from a useful
record can supply a misleading initial capture after injury, even while the
incoming record remains intact.

The packet diagnostics are consistent with this lead. In that same informative
negative-half group, own-code projection falls from 0.179419 to 0.116838 over
the first repair. In the positive-half group it rises from 0.182135 to 0.249523.
For injuries retaining both polarities, packet projection onto the injury
half-plane rises from 0.004537 to 0.108204. That axis is orthogonal to the
intended code in this group. These geometric measurements do not themselves
estimate record capacity; the paired next-body scores above supply the
receiving test.

The loss is not an immediate catastrophic byte change at update one. Across
informative records, the first updated packet has mean correlation 0.999999
with the incoming packet and mean RMS displacement 0.000410. At the end of
the repair episode these become 0.803799 and 0.171905. Every first native
write satisfies the frozen writing equation, and every outgoing packet is
exactly the input to the next saved body. Only updates 0, 1 and 1,000 were
saved, so the precise failure time within the episode remains unknown.

Body recognition and record usefulness remain separate. Immediately injured
informative bodies score 25.000% under the code-ranking diagnostic; repaired
bodies score 58.203%, and their outgoing records give 61.328% in the next
fresh body. Many injured bodies with incorrect rankings still produce useful
records. The complete eight-cell developed/injured/next-body transition table,
all seven policies and all message/block strata are retained in the summary.
None of these body observations should be relabeled as individual capacity.

The next useful counterfactual is to remove only the known replacement-fill
component from captured memory while keeping the actual injured body, incoming
record and stochastic environment fixed. A writing-on/off comparison and a
zero-memory comparator would separate feedback and packet effects. Such a
variant uses the injury mask, an additional supplied resource absent from the
original capture rule; it must disclose that information boundary. The
[prepared next-step design](FIRST_REWRITE_NEXT_STEP.md) is a proposal, with no
new simulation or frozen confirmation launched here.

The main diagnostic passes twelve qualification checks and verifies 2,350
bound inputs, all 3,584 first-episode rows and 512 matched capture/one-time
pairs. It completes in 126.90 seconds. The fill decomposition retains all 512
capture rows and checks every additive identity and scalar projection.
Original run files, all frozen physics and the completed TT022 result remain
unchanged. Resource admission used one numerical thread; sleeping controller
threads were distinguished from nine active or CPU-consuming project threads.
